**잘한 점**

- **`-l 11`(원래 뇌 코덱, 64MB 블록)이 5개 데이터 모두에서 가장 작아요.** 위키백과 텍스트·표준 세트·설치 폴더에서는 xz·7z의 최고 압축보다 **12~18% 더 작고** 여러 버전 백업에서는 3~5%, 실행 파일에서는 7z보다 5.1%, xz보다 14% 더 작아요.
- **`--max`(빠른 뇌 코덱, 16MB 블록)는 `-l 11`보다 압축·해제가 1.6~2.3배 빨라요.** 파일 하나 꺼내기는 5.4~6.3배 빨라져서 76~112초 걸리던 게 14~20초가 됐어요. 코어가 4개인 맥에서는 차이가 4배쯤이에요(텍스트 48MB 압축 38초 → 9초, 해제 41초 → 10초). 텍스트에서는 여전히 xz보다 한참 작고(위키백과 13.3%, 표준 세트 10.9% 작음) 압축 시간은 모든 데이터에서 xz -9e보다 짧아요(위키백과 53초 vs 150초).
- **작은 파일에서는 뇌 코덱이 더 크게 앞서요.** 예시 글과 코드, 데이터 75KB로 미리 배운 상태(타고난 지식)에서 시작하기 때문이에요. 작은 파일 15개를 합치면 `--max`가 xz -9e보다 19.9%, zip -9보다 26.4% 작고 파일 하나하나를 봐도 `--max`보다 작은 건 `-l 11`뿐이에요.
- **기본 레벨도 같은 타고난 지식을 zstd 사전으로 써요.** 1MB 이하 블록에 적용되고 작은 파일 15개에서 ezpz 0.3.0보다 5.4% 작아졌어요. 이제 모든 파일에서 zip -9보다 작고(합계 7.5%) 합계는 xz -9e와 0.6% 차이예요.
- **실행 파일이 모든 레벨에서 작아졌어요.** ezpz 0.3.0과 비교해 `-l 3`은 3.5%, `-l 11`은 10.5% 작아요. 64비트 x86 프로그램은 이제 기계어 속 호출 주소와 데이터 주소를 코드에서 빼서 파일 끝에 모아요. 7z의 BCJ2와 비슷한 생각이에요. 남은 코드는 빌드가 다른 같은 프로그램끼리 그대로 맞아떨어지고 큰 프로그램에서는 8MB보다 멀리 떨어진 주소도 바꿔요. 다만 서로 관계없는 작은 라이브러리 묶음에서는 이 방식이 1.5%쯤 손해라서 레벨 4 이상에서는 인코더가 두 방식을 빠르게 시험해 보고 나은 쪽을 골라요. 파이썬 데이터 두 개에서는 예전처럼 제자리에서 바꾸는 방식이 뽑혔어요.
- **기본값(`-l 7`)은 tar.zst -19 --long과 크기가 거의 같아요.** 커 봐야 2.4%이고 표준 세트에서는 조금, 실행 파일에서는 5.6% 작아요. 압축은 모든 데이터에서 더 빠르고(표준 세트 78초 vs 113초) 해제는 1초 안쪽이에요. 게다가 tar.zst는 못 하는 **파일 하나 꺼내기가 0.1초 이하**예요.
- **`-l 3`은 zip보다 10~33% 작으면서 압축은 5.6~26배 빨라요.** (백업 데이터: zip 41.9초 → ezpz 1.6초)
- **`-l 9`는 xz·7z와 크기가 비슷해요.** 표준 세트와 설치 폴더에서는 셋 중 가장 작고 실행 파일에서는 7z와 1.7% 차이예요. 해제와 파일 하나 꺼내기는 더 빨라요(표준 세트에서 파일 하나: 1.0초 vs xz 4.3초, 7z 3.5초).
- 해제 결과는 모든 경우에 원본과 바이트 단위로 같았어요.

**부족한 점 (솔직하게)**

- **`--max`는 프로그램 파일과 백업에서 크기를 내줘요.** 설치 폴더, 백업, 실행 파일에서 `-l 11`보다 13~15% 커요. 7z와 비교하면 백업에서 11.5%, 실행 파일에서 6.8% 크고 이 두 데이터에서는 `-l 9`가 더 작으면서 해제도 훨씬 빨라요. 손해의 대부분은 16MB 블록에서 나와요. 64MB 블록보다 파일 사이의 비슷한 부분을 덜 활용하거든요. 이런 데이터를 가장 작게 만들려면 `-l 11`을 쓰세요.
- **뇌 코덱은 둘 다 해제가 느려요.** `--max`도 이 서버에서 초당 약 2MB(코어 4개인 맥에서 약 5MB)라 xz보다 수십 배 느려요. 자주 여는 파일보다는 오래 보관할 파일에 맞아요.
- **실행 파일에서 zstd·LZMA2 레벨은 아직 7z에 못 미쳐요.** `-l 9`가 7z보다 1.7% 크고 7z보다 작은 건 뇌 코덱을 쓰는 `-l 11`뿐이에요. 레벨 1~3은 빠르게 끝나도록 두 주소 처리 방식을 시험하지 않는데, 그 탓에 파이썬 데이터 두 개에서 최대 0.13% 커졌어요.
- **작은 파일 15개 중 6개에서는 기본값이 아직 xz -9e보다 커요.** JSON·표·XML 데이터와 스페인어·일본어 글이에요. ezpz 목록이 아카이브마다 250바이트쯤(대부분 해시) 붙는 것도 한 원인이에요.
- **메모리를 많이 써요.** `-l 9`는 압축할 때 zstd 22와 LZMA2 9e를 블록마다 둘 다 시도해서 1.2~1.6GB를 써요. 뇌 코덱은 2스레드 기준 `--max`가 0.4~0.55GB, `-l 11`이 0.4~0.9GB예요.
- **기본값은 tar.zst -19보다 최대 2.4% 커요.** 블록으로 나눠서 병렬 처리와 파일 하나 꺼내기를 얻은 대가예요.
- 모든 수치는 한 번씩 잰 값이고 느린 가상 서버 기준이에요. 맥 미니(Apple Silicon)에서는 모든 도구가 더 빠를 거예요.

**다음 개선 후보**

- 폴더에서의 `--max`: 병렬 해제는 유지하면서 16MB 블록끼리 배운 내용을 나누기
- 애플 실리콘 같은 ARM64용 프로그램: x86-64처럼 호출 주소를 코드에서 빼서 모으기
